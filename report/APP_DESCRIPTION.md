## 1. What Riaya is

Riaya is an AI-powered doctor appointment platform made for Tunisia. It has two sides:

- **Patients** book by **phone call**. An AI voice assistant answers, speaks Tunisian Arabic (Derja), French or English, finds a nearby doctor with a free slot, and sends the doctor a booking request. Patients have **no account and no website**. They only use the phone and WhatsApp.
- **Doctors** run their practice from a **web dashboard**: calendar, patients, invoices, medical files, consultation recordings with transcripts, an AI assistant, WhatsApp messages and a subscription.

Two more roles support this: **secretaries** (who work inside a doctor's practice) and **administrators** (who run the platform).

The phone call is the most important feature. It is the reason patients use Riaya, so most of our testing time went into it.

## 3. Architecture and technology

Riaya is split into **two repositories**:

- **`web/`**: the Next.js app. It holds the website, the doctor and admin dashboards, all API routes and the database layer.
- **`voice/`** (package `riaya-realtime`): the realtime server. It talks to Twilio, runs the AI phone call, streams live call events to the admin dashboard, runs the WhatsApp connections and runs the background workers. It also contains a separate **LiveKit agent** process.

### Technology

| Area | Choice |
|---|---|
| Web framework | Next.js 16 (App Router), React 19, TypeScript |
| Styling / UI | Tailwind CSS v4, shadcn/Radix/Base UI components |
| Data fetching | SWR; API client generated by **Orval** from an OpenAPI spec produced by `zod-to-openapi`. Every API route registers its schema. |
| Forms | React Hook Form + Zod |
| Auth | Better Auth (email + password) |
| Database | PostgreSQL through Drizzle ORM (migrations with `drizzle-kit`) |
| Calendar / maps / PDF | react-big-calendar, Leaflet, pdfkit |
| Realtime server | Node.js, Express 5, `ws`, Pino logging |
| Phone | Twilio (inbound calls, outbound callbacks, call recording) |
| Phone AI | **Gemini Live** (`gemini-3.1-flash-live-preview`, voice Puck) in production (`BACKEND=gemini`). OpenAI Realtime, GPT-Live and Inworld stay available (switch with `BACKEND`), and so does the LiveKit agent (speech-to-text → LLM → text-to-speech) |
| Doctor AI | OpenRouter (chat model `deepseek/deepseek-v4-flash-0731` by default; transcription `microsoft/mai-transcribe-2`) |
| WhatsApp | Baileys (one linked session per doctor) |
| Jobs | BullMQ + Redis |
| Files | Cloudflare R2 with presigned upload URLs, public CDN URL stored on the record |
| Payments | Konnect.network |
| Email | Nodemailer (sign-up OTP, secretary invites) |
| Maps / places | **Google Places** is the chosen provider for finding places; Geoapify was only a test provider for places. The code can switch with `GEO_PROVIDER`. Road distance comes from the Geoapify Route Matrix |
| Package manager | pnpm |
| Lint/format | Biome |

### How a phone call flows

1. A patient dials the Riaya number. Twilio sends a webhook to the voice server (`/incoming-call`).
2. The server first asks the web app if the number is **blocked** (see [Section 9](#9-abuse-reports-and-blocked-numbers)). If so, it answers with a Twilio `<Reject reason="busy"/>` and no AI starts.
3. Otherwise the server creates the **call row** and finds or creates the **person** for that phone number (both cached, run in parallel).
4. It answers with TwiML. Depending on `CALL_ROUTER`, the call goes to a **media stream** WebSocket (`/media-stream`) handled by `TwilioSession`, or to **LiveKit over SIP** for the LiveKit agent.
5. `TwilioSession` bridges three connections: Twilio audio (μ-law 8 kHz), the realtime AI model, and the **dashboard** WebSocket so admins can watch the live transcript.
6. The AI calls tools. Tools call the web app's internal API (`x-internal-secret` header): find slots, book, cancel, update the person.
7. When the call ends, the call row is completed and events are stored in `call_event`. The voice server starts a Twilio recording when it answers; the finished recording is sent to a web webhook that saves it to R2.

### Server-to-server security

Routes under `/api/internal/*` and the call/person routes used by the voice server require the shared secret `INTERNAL_API_SECRET` in the `x-internal-secret` header. The Twilio recording webhook is public but checks Twilio's `X-Twilio-Signature` (HMAC-SHA1).

## 4. Accounts, sign-up and doctor verification

### Sign-up with email OTP

- The sign-up form asks for **email, password and password confirmation**. The password must have at least 8 characters, with letters and numbers.
- Riaya emails a **6-digit OTP**. It is valid for **10 minutes**, allows **5 attempts**, and a new one can be requested after a **60-second cooldown**.
- The pending sign-up (OTP hash and the password encrypted with AES-256-GCM) is kept in Better Auth's `verification` table. The user row is created only after the OTP is verified. The user is then signed in.
- New users get a default doctor avatar.
- The same sign-up page is used for **secretary invitations** (the email is pre-filled and the user returns to the invite link afterwards).

### Doctor application and verification

After sign-up a doctor can open **only the Profile page**. They fill in and submit an application:

- first name, last name
- **CIN** (national ID) front and back pictures
- **speciality**
- **Medical Council** registration number and certificate
- **cabinet name**, **TIN** (tax ID: 7 digits and 1 uppercase letter), **cabinet city**
- the exact **cabinet location chosen on a map** (latitude and longitude)

Documents are uploaded straight to Cloudflare R2 with a presigned URL; only the CDN link is stored.

Application and profile statuses: `none` → `pending` → `verified`, or `rejected`, or `banned`.

| Admin action | Result |
|---|---|
| **Approve** | A `doctor_profile` is created or updated from the application, the user's display name is set, status becomes `verified`, and the full dashboard unlocks. |
| **Reject** (with optional reasons) | The doctor stays limited to Profile, sees the reasons, fixes the information and **reapplies** (back to `pending`). |
| **Ban** | The doctor is blocked. |

Until a doctor is verified, every other dashboard page redirects to Profile.

### Profile after verification

- Profile picture (cropped in the browser, uploaded to R2).
- **Invoice branding** (Pro only): logo and stamp, PNG or JPEG.

## 5. Plans, limits and payments

All numbers below come from `lib/plans.ts` and `lib/plan-limits.ts`.

### The two plans

| | **Free** | **Pro** |
|---|---|---|
| Price | 0 TND | **49 TND / month** |
| AI phone booking | **Unlimited** | **Unlimited** |
| Patients, appointments, availability, calendar | Yes | Yes |
| Invoices (create, payments, cancel, WhatsApp send) | Yes | Yes |
| Medical files | Yes | Yes |
| WhatsApp sends started by the doctor | **30 / month** | **Unlimited** |
| Recording + transcription time | **2 hours / month** | **100 hours / month** |
| Buy extra recording hours (packs) | No | **Yes** |
| AI consultation note on each transcribed recording | No | **Yes** |
| AI assistant allowance | about **20** questions / month | about **2,000** questions / month |
| Doctor logo and stamp on invoices | No (footer "Facture générée avec Riaya") | **Yes** |
| Secretary accounts | None | **Unlimited** |
| Support | Standard | Priority |

Marketing copy says "about N questions" and the app shows usage as a **percentage**.

### How limits are counted

All monthly counters reset on the **UTC calendar month**.

- **Effective plan.** A doctor is on Pro only if the subscription is `pro`, its status is `active`, and its period end is still in the future. A missing, free, `past_due` or expired Pro behaves as **Free**.
- **WhatsApp sends (Free only is limited).** Only sends the doctor starts count:
  - a medical file with documents = **1 caption + 1 per document** (N documents = N+1 sends);
  - a text-only medical file = 1;
  - an invoice PDF = 1.
  - **Automatic patient messages are never counted and never blocked**: appointment confirmations, review requests, timeout and refusal messages.
  - The check is atomic in SQL (`sendCount + count <= limit`). When the limit is reached the API returns `WHATSAPP_LIMIT_REACHED`.
- **Recording time.** A recording uses its audio length once it is **transcribed** (re-running a transcription does not count again).
  - The plan's monthly hours are used first. After that, **pack hours** are used (Pro only). Pack hours never expire.
  - A recording that overruns the last minutes is not cut off.
  - A per-doctor database advisory lock keeps two charges from racing.
  - Usage rows stay after a recording is deleted, so deleting never gives time back.
  - **Recording always works**, even with no time left: the audio is saved with status `skipped` ("Not transcribed"). The doctor can transcribe it later with one click when time is available. It is never transcribed automatically later.
  - Consultation notes (summaries) are **covered by the recording hours**, with no separate limit.
- **AI assistant budget.** Measured in **real model cost** reported by OpenRouter for each reply (stored in millionths of a USD on the message).
  - Free budget: **$0.05** per month. Pro budget: **$5** per month (about 15 TND).
  - A typical question is estimated at $0.0025, which gives the "about 20" and "about 2,000" figures. Long chats, attached transcripts and questions that look up practice data cost more, so they give fewer questions.
  - A new question is refused (`AI_USAGE_LIMIT_REACHED`) once the month's budget is spent. A reply's cost is only known afterwards, so the last one can go slightly over.
  - The budget itself stays on the server; doctors only see a percentage.

### Recording hour packs (Pro only)

| Pack | Hours | Price |
|---|---|---|
| `hours_25` | 25 h | 15 TND |
| `hours_100` | 100 h | 50 TND |

Bought on **Subscription → Add hours**, paid through Konnect. Free doctors get `RECORDING_PACKS_REQUIRE_PRO`.

### Payments with Konnect.network

Konnect has no native subscriptions, so Riaya manages the cycle itself.

1. **First upgrade.** `POST /api/billing/checkout` starts a Konnect payment (no invoice yet, `orderId = upgrade:<subscriptionId>`). If the doctor is already on Pro with a valid period, it returns `alreadyActive`.
2. **Webhook.** Konnect calls `GET /api/webhooks/konnect?payment_ref=...` on every status change. When the payment is `completed`:
   - for a first upgrade: Pro is activated for **one month**, and a paid `billing_invoice` is created (numbered `INV-YYYY-NNN`);
   - for a renewal or a pack: the open invoice is marked paid; a paid `subscription` invoice activates Pro for the invoice period; a paid `top_up` invoice is what grants the pack hours.
   - The webhook is **idempotent** (a paid invoice or an already-active Pro is ignored) and always answers `200`.
3. **Renewals.** A daily BullMQ job (08:00 UTC, plus one run at startup) calls `POST /api/internal/subscriptions/process-expiring`. For every active or `past_due` non-free subscription ending **within 3 days**, it creates an **open billing invoice** for the next month with a Konnect payment link (unless one already exists). The doctor sees it on the Subscription page and **must pay it to keep Pro**.
4. **Dev mode.** With `BILLING_DEV_BYPASS=true`, checkout returns a fake `/dev/pay` page that still finishes through the real webhook.

There is no in-app "downgrade" button: letting Pro expire returns the doctor to Free.

## 6. The phone assistant (patients call Riaya)

### Identity and profile

- The patient's **phone number is their identifier**. It comes from the call, so the AI **never asks for it**.
- On each call Riaya loads the **person** for the number: first name, last name, date of birth, gender, address and **preferred language**. The AI greets by name when it knows it.
- It also loads **everyone known on that line** (the owner and family members) so it can ask "is it for you or for Adam?". The prompt lists them as "PEOPLE ON THIS LINE" with their ids.
- **Preferred language** is `ar` (Tunisian Derja) by default, and can become `en` or `fr` if the patient asks to switch. It is saved, used for the next call and for WhatsApp messages. Mixing a few French or English words into Derja is not a language switch.

### Languages and style

- Supports **English, French and Tunisian Arabic (Derja only)**. It must never use Egyptian or other dialects.
- Speciality and city names are said in the patient's language. **Doctor names are always pronounced in Arabic**.
- **Very short replies** (1 to 2 sentences) and **one question per turn**.
- Stays on topic: bookings and the caller's own AI bookings. Small talk gets a short polite reply. Medical advice, general questions and prompt-injection attempts are refused briefly.
- It **never gives medical advice or a diagnosis**.
- Times: patients speak in **Tunisia time (GMT+1)**; tools use **UTC (ISO 8601 ending in `Z`)**. The AI converts both ways.

### Normal booking flow

1. Greet (by name if known). If the name is unknown, ask once and save it.
2. Ask for the **reason or symptoms**, unless the patient already names a speciality or doctor type (then skip).
3. Choose a **speciality** and confirm it with the patient. If unclear after 3 clarifying questions, offer to book a **General Practitioner**. Defaults: joint/muscle/bone pain → Rheumatology; vague symptoms → General Practice. **Surgical specialities are never suggested** unless the patient states a confirmed diagnosis or surgical referral.
4. Ask for the **location**: city plus region or street. Geocode it (restricted to Tunisia). If several places match, offer 2 to 3 and ask. If nothing is found, ask for more detail or fall back to the city list.
5. Ask for the **preferred date and time** (no preference = now).
6. Run the **best-fit search** and present the **top 2 to 3 options**: doctor, cabinet address, distance in km, time.
7. The patient picks one, asks for other times, or asks about one doctor. The AI keeps searching until they choose or stop. It never says "no slots" after one try.
8. **Book** a **pending** request with the exact doctor id, the patient, the reason and the slot.
9. Say the request was **sent** (never "confirmed", because the doctor must accept), then end the call with a short goodbye.

### A specific doctor by name

At any point the patient can name a doctor. The AI looks the name up in Latin letters (up to 5 results), confirms, then shows that doctor's slots. Speciality and city are not needed.

### Who the appointment is for

- By default for the caller. A caller can book for someone else on the same phone (child, parent, spouse, sibling, other).
- A listed person is booked by id; a new person is booked with a first name, last name and **relationship to the phone owner**.
- If the caller is not the phone owner (for example, a wife using her husband's phone), the AI treats her as a new family member and does **not** overwrite the owner's profile.
- The reason (`illness`) always describes the patient, not the caller.

### Existing bookings

- The AI can **list** the caller's AI appointments (up to 3 upcoming pending/confirmed, plus one recent past within 30 days) with doctor, address, time and status.
- It can **cancel only `pending`** appointments. Cancelling an urgent pending request cancels the whole emergency group.
- For a **confirmed** appointment it cannot cancel or change anything; it tells the patient to contact the doctor's office, and can still read out the address and time.
- The caller's phone always comes from Twilio, never from the AI.

### Life-threatening signs and emergency mode

- For signs such as chest pain, trouble breathing, stroke signs, heavy bleeding, fainting, a seizure or a serious injury, the AI first tells the patient to call the **SAMU at 190**, then asks if they also want urgent requests sent to nearby doctors.
- For urgent but not life-threatening cases, it asks if the patient wants the **closest available doctors right now**. If yes:
  1. A search runs for the earliest slots (preferred time = now, same distance rules).
  2. **Up to 3 pending appointments** are created, all marked **urgent**, sharing one **emergency group id**.
  3. Doctors see an **urgent badge** and a stronger notification.
  4. The **first doctor to accept keeps the booking**; the other pending requests in the group are cancelled automatically.
  5. If a doctor only refuses their own request, the others stay open.
  6. If the patient cancels one pending urgent request, the whole group is cancelled.
- Emergency requests are never blocked by doctors' plans. (There is no AI booking limit on any plan anymore.)

### Tools the AI can call

`get_specialities`, `get_cities`, `search_location`, `find_available_slots`, `find_doctor_by_name`, `find_doctor_slots`, `book_appointment`, `book_emergency_appointments`, `update_person_info`, `list_my_ai_appointments`, `cancel_appointment`, `end_call`, `report_abuse`.

### Callbacks (Riaya calls the patient)

When a request is refused or times out (see [Section 8](#8-after-a-booking-accept-refuse-timeout-review)), Riaya places an **outbound call**. The AI opens the conversation itself with a callback script. For a refusal, the first thing it offers is up to 3 other doctors with free slots.

### Silent callers and call length

A shared `CallWatchdog` (used by both the media-stream path and the LiveKit agent):

- once the assistant is quiet, it waits **12 s**, then asks once "are you still there?";
- if the caller stays silent for **10 s** more, it says goodbye and hangs up;
- any call ends with a polite goodbye at **15 minutes**.

Silent calls are logged as a `system` event, not as abuse.

### Audio and transcripts

- Twilio audio is μ-law 8 kHz with a noise gate/suppression step in `audioProcessor.ts`.
- The caller's words are shown on the admin dashboard. A separate **caller transcriber** splits the caller's audio into sentences with an energy check and sends each to a transcription model (default: `google/gemini-3.1-flash-lite` through OpenRouter). It exists because the realtime model's own input transcript was very inaccurate in our tests. It can be turned off (`CALLER_STT=off`).
- **Call recordings.** When Twilio finishes a recording, it calls the web app's recording webhook, which downloads the audio (as MP3), uploads it to R2 and stores the link on the call row. The voice server starts a two-channel recording through Twilio's API right after it answers the call (`api/callRecording.ts`), unless the caller is blocked. It needs `WEB_PUBLIC_URL` set; without it, recording is off. Admins listen to it in Live Calls and in abuse reports.

## 7. Finding the right doctor (best fit)

Used by the phone assistant and by the admin Best Fit Finder.

1. **Location.** The patient's place is geocoded with **Google Places**, restricted to Tunisia (the code keeps a switch, `GEO_PROVIDER`, that also supports Geoapify, which we only used for testing). A `sessionToken` ties Google's autocomplete and details calls into one billed lookup. If a precise place is not found, the AI falls back to the stored list of **24 Tunisian cities** with GPS coordinates. Doctor cabinets store exact latitude and longitude from the registration map, so matching is coordinate to coordinate.
2. **Candidates.** Only **verified** doctors with the chosen speciality and a mapped cabinet.
3. **Radius.** Doctors farther than **50 km** (Haversine) are excluded. This stops a Sfax doctor being offered to a Tunis patient. **Fallback:** if no doctor inside 50 km has a slot, the **3 nearest** doctors beyond it are returned, flagged `farAway`, and the AI tells the patient honestly.
4. **Slots.** For each doctor, find the nearest free **30-minute slot** around the preferred time within the next week, searching both before and after, skipping appointments and the doctor's weekly availability limits. Up to **3 extra forward slots** are returned so the AI can offer alternatives without another search.
5. **Score.** `distance (km) + |slot − preferred time| (minutes) / 10`. Lower is better. So 10 minutes of waiting counts like 1 km. The time delta is measured against what the patient asked for, not against "now".
6. **Road distance polish.** The top **8** straight-line candidates are re-ranked with real **driving distance** from Geoapify Route Matrix (one call per search, about 8 credits, 3-second timeout). If the service is slow or fails, the straight-line order is kept.
7. **Kilometres only.** The assistant speaks distance in km and never drive time.

### Road-distance experiment (from `BEST_FIT_DISTANCE.md`)

78 comparisons (4 specialities with the most doctors × 24 city centres), top 8 by straight line:

| Measure | Result |
|---|---|
| Best doctor changes (road km) | 24 of 78 (31%) |
| Best doctor changes (drive time) | 19 of 78 (24%) |
| Time saved when it changes | median 0.8 min, max 4.1 min |
| Searches saving 5 minutes or more | 0 |
| Road ÷ straight distance, typical | 1.01 |
| Road ÷ straight distance, worst 10% | 1.9 or more |
| Road ÷ straight distance, worst case | 3.27 |

Conclusion: straight line is the right first filter; road distance is a light polish whose main benefit is quoting a real road distance to the patient. Limits of the test: distance only (no appointment times), city-centre patients, local data that may include test doctors, and only the 8 nearest were checked.

Admins can run the same search on a **map and calendar** (Best Fit Finder) and open any doctor's availability.

## 8. After a booking: accept, refuse, timeout, review

### Pending requests

A phone booking creates an appointment with `source = ai` and `status = pending`. It appears **in real time** on the doctor's calendar (WebSocket). The booking records `personId` (who it is for) and `contactPhone` (the line that booked, where messages go).

### Accept

- Status becomes `confirmed`.
- The visit is linked to that person's **patient file**: an existing file is matched automatically (doctor + person); otherwise the doctor picks a patient or creates one. Phone bookings from unnamed callers must be accepted from the calendar.
- The patient gets a **WhatsApp confirmation** in their preferred language (automatic, **not counted** against the plan).
- A **review request** is scheduled for **2 hours after the appointment ends**.
- Urgent request: accepting it **cancels the siblings** at other doctors.

### Refuse (decline)

- The appointment becomes `cancelled`.
- For a **normal** request, Riaya remembers what the patient asked for (speciality, area, time, doctors who already said no) in Redis for **24 hours**, then **calls the patient back** (or sends a WhatsApp) with up to **3 other doctors** that have fresh slots. The phone AI offers these first on the patient's next call.
- For an **urgent** request, nothing is sent; other doctors can still accept.

### Unanswered for 10 minutes

- A delayed BullMQ job auto-**cancels** a pending AI request (or an urgent group where nobody accepted) after **10 minutes**.
- Riaya then **calls the patient back** through Twilio with a short script asking them to call again to book with another doctor.
- If calling is not configured, or the patient does not answer (`no-answer`, `busy`, `failed`, `canceled`), Riaya sends the same message on **WhatsApp** from the **platform (admin) WhatsApp account**.
- Blocked numbers get no callback and no WhatsApp.

### Patient cancels

By phone, while `pending` only. Confirmed appointments need the doctor's office.

### Review

- 2 hours after the appointment end, the review worker checks the appointment is not cancelled, that no review exists for this patient and doctor, and that a phone number is known.
- It creates a `review` row with a unique token and sends a WhatsApp message in the patient's language with a **link `/review/<token>`**.
- The patient rates the doctor on that page: **rating, wait time, comment**, **no account needed**. A token can be used once (`REVIEW_ALREADY_SUBMITTED`).

## 9. Abuse reports and blocked numbers

- **When the AI reports.** The prompt says: one calm warning for mocking or insults; `report_abuse` immediately for threats or sexual talk; never for confusion, frustration, elderly callers, bad lines, children, jokes, or questions like "are you a robot". If unsure, it is not abuse. The AI never says the call is reported or the number is blocked, and it never blocks.
- **What a report holds.** `call_report`: one per call, with a category (`mocking`, `insults`, `threats`, `sexual`, `other`), an English summary written by the AI, a status (`open`, `dismissed`, `blocked`), and who reviewed it and when. The AI then says one neutral goodbye and hangs up.
- **Admin review.** The **Reported Calls** page (`/admin/reports`) is a queue with the call recording and transcript, plus context about the number. The sidebar shows a badge with open reports. The admin can **dismiss**, **reopen**, or **block** the number.
- **Blocking.** `blocked_phone` (phone is the primary key). Durations: **7 days, 30 days or permanent**; an admin can change the duration or unblock. A number is blocked while a row exists and has not expired.
- **Enforcement.** In `/incoming-call`, before any AI session: blocked callers get Twilio `<Reject reason="busy"/>`. The check counts each rejected attempt (`rejectedCallCount`, `lastRejectedAt`). It **fails open** (about 1.5 s timeout), so a web outage never turns patients away. It covers the media-stream and LiveKit paths.

## 10. The doctor dashboard

Sidebar (doctor): **Dashboard, Patients, Appointments, Invoices, Recordings, AI Assistant, Availability, Profile, Team, WhatsApp, Subscription.** An **AI button** at the bottom right of every page opens the assistant in a side panel (shortcut ⌘J / Ctrl+J).

### Dashboard home

Practice overview: today's and upcoming appointments, pending bookings, number of patients, unpaid invoices, **revenue collected this month** and **outstanding**, 14-day charts (by day, status and source), and plan usage meters (WhatsApp, recording time, AI allowance). The same numbers feed the AI assistant's `get_practice_stats` tool.

### Patients

- **Add a patient**: first name, last name, date of birth (typed or from a calendar; age shown), gender, CIN (all required), phone (required), address (optional). Phone entry uses the shared phone input with country picker and validation.
- **"This number belongs to someone else"**: pick the relationship (child, parent, spouse, sibling, other). The patient is filed as a family member on that phone instead of becoming its owner.
- **Patient page**: edit details (editing never changes which person on the phone the file belongs to), a **History** timeline of medical files and recorded consultations (newest first), and the patient's invoices.
- **Medical files**: types `consultation`, `prescription`, `lab-report`; title (required), date, description, up to **10 documents** of **20 MB** each (PDF, images, Word). Can be **sent on WhatsApp** (patient needs a phone, doctor's WhatsApp must be linked, counts toward the limit). Can be sent again.
- Doctors can add a patient manually or link one when accepting an AI booking. A secretary sees patients **without medical files**.

### Appointments (calendar)

- Statuses: `pending`, `confirmed`, `cancelled`. Sources: `dashboard` (starts confirmed) and `ai` (starts pending).
- Create by dragging on the **30-minute grid**; pick patient (required), name/reason (required), description (optional). Drag to move, click to edit. Overlaps are refused. Times outside weekly availability cannot be chosen (if no availability is set, any time is allowed).
- Pending phone bookings show the patient, symptoms and time, with **Accept / Refuse**. Urgent ones have a **red badge**. New requests appear live with a notification sound.
- Confirmed appointments: edit name/description, cancel or delete.

### Availability

Weekly working hours: for each weekday open/closed, **one From–To range per open day**. The default form pattern is Monday to Friday 09:00–17:00. Used by the calendar and by the AI slot search. There is no separate holiday calendar in the UI (a `doctor_unavailability` table exists in the database).

### Invoices (patient billing)

- Create from the Invoices page or a patient's page: lines with description, quantity (≥ 1) and unit price in TND; optional notes. Numbers are **`INV-YYYY-NNNN` per doctor**.
- Statuses: `unpaid`, `partially_paid`, `paid`, `cancelled`. Status is **derived from payments** against the total; cancel is a soft state.
- **Payments** are a list of events (not one field): methods `cash` or `transfer`; cannot exceed the remaining balance; cannot pay a cancelled invoice; payments can be deleted and the status re-syncs.
- **PDF** is built with pdfkit. On Pro it shows the doctor's **logo and stamp**; on Free it shows the Riaya footer. **Send** builds the PDF and sends it on WhatsApp (1 send).
- Amounts are stored in **millimes** (1 TND = 1000). Column names say `*Centimes` for historical reasons.

### Profile

Application status, personal and cabinet details, picture, and (Pro) **invoice branding**.

### Subscription

Free vs Pro, usage meters, **Upgrade to Pro** (Konnect), open Riaya billing invoices to pay, **Add hours** (packs, Pro), and invoice history.

### Error handling and UX rules

Errors use stable codes (`lib/errors.ts`) with a user-facing message map. Forms keep drafts. Mobile and desktop are both supported.

## 11. Consultation recordings

- **Record in the browser** on Recordings → New Recording, with an optional patient and title. Recordings under **2 seconds** are not kept.
- **Safe by design.** While recording, the audio is also kept in the browser (IndexedDB). If the tab closes or crashes, the Recordings page offers to save it next time. Leaving mid-recording asks first. If saving fails, the audio is kept with a **Try again** button.
- **Upload.** The audio goes to R2 with a presigned URL.
- **Transcription starts automatically** after saving, when recording time is left. The model is `microsoft/mai-transcribe-2` through OpenRouter, with **speaker diarization**.
- **After the transcript**, one cheap AI call gives:
  - a short **English title** (3 to 6 words) if the doctor left it empty (a title the doctor typed is never replaced);
  - a **role for every speaker**: `doctor`, `patient` or `companion` (for example a parent speaking for a child). The doctor can fix wrong roles in the **Speakers** row, and it updates everywhere in the transcript.
- **Consultation note (Pro).** An automatic structured note written **in French** from the transcript: reason, history, examination, assessment, plan. It uses only what was said, never invents a diagnosis, can be edited and can be rewritten.
- **Discuss with AI** opens the assistant with the transcript attached (only transcripts whose status is `done`).
- Statuses: `pending`, `processing`, `done`, `error`, `skipped`.
- Recordings can be linked to a patient and appear in the patient's History. They can be deleted (the time used is not returned).
- Recordings are **doctor-only** (secretaries cannot see them).

## 12. The AI assistant for doctors

### What it is

A chat assistant inside the dashboard, for **doctors only** (not secretaries). It is decision support for the doctor, not a patient chatbot. It replies in the doctor's language (Arabic, Derja, French, English or a mix).

### Where

The AI Assistant page, or the side panel opened from any dashboard page. The panel keeps its conversation while the doctor changes pages and **knows the page** (on a patient's file, "this patient" means that patient). On wide screens the page makes room for it; on small screens it opens over the page.

### What it can do

1. **Medical help**: differentials, red flags, work-up ideas, note drafting, consultation review. When a transcript is attached it answers from the transcript first. It always reminds the doctor that clinical decisions stay theirs.
2. **Product help**: exact steps, menu paths and limits for every Riaya feature. The guide is injected on every turn and reads plan numbers from `plans.ts`, so it never goes out of date.
3. **Look up the practice** with read tools, shown as cards:

| Tool | What it returns |
|---|---|
| `get_schedule` | Appointments for any days |
| `get_pending_bookings` | Phone bookings waiting for a decision |
| `search_patients` | Patients by name or CIN |
| `get_patient_summary` | A patient's visits, medical files, consultation notes, unpaid invoices |
| `get_free_slots` | Free slots on a day |
| `get_invoices` | Invoices |
| `get_practice_stats` | Today, this week, revenue, outstanding |

4. **Propose changes** with action tools. Each one shows a card the doctor can edit, then **Confirm** or **Dismiss**. **Nothing changes until the doctor confirms.** Cards warn about overlaps, times outside opening hours and times in the past.

| Tool | Proposal |
|---|---|
| `propose_invoice` | Create an invoice (asks for the price if missing) |
| `propose_booking_decision` | Accept or refuse one pending booking (accepting sends the WhatsApp confirmation and creates a patient file if needed) |
| `propose_medical_note` | Save a consultation note, prescription or lab report |
| `propose_appointment` | Book a confirmed appointment |
| `propose_reschedule` | Move an appointment |

### What it cannot do

Record or delete payments, send invoices or files on WhatsApp, cancel or delete invoices, delete appointments or patients, edit patient details, change opening hours, manage the team or subscription. It says so and points to the right page.

### How it works

- **Model:** OpenRouter chat model `deepseek/deepseek-v4-flash-0731` (changeable with `OPENROUTER_CHAT_MODEL`).
- **Privacy:** every call is sent with `zdr: true` and `data_collection: deny`, so only providers that neither keep nor train on the request are used, because chats can contain patient data.
- **Agent loop:** up to **6 steps** per reply; at most 20 past messages are sent to the model; only the last 2 replies keep full tool results. Bad arguments or wrong ids go back to the model as errors so it can retry; the doctor never sees those.
- **Never invents ids.** The model gets patient ids from `search_patients` and appointment ids from the schedule tools. Ownership is checked on the server for every id.
- **Time:** all dates are Africa/Tunis wall-clock time; amounts are millimes in tools and TND in speech.
- **Saved and resilient.** Messages are made of **parts** (text, tool result, proposed action). A reply is created as `streaming` and saved every 0.75 s, so it **keeps being written and saved even if the doctor closes the page**. A doctor can stop it (`stopping` → `stopped`). Stale replies expire after 5 minutes. Only one reply can run per conversation at a time. Each reply stores prompt tokens, completion tokens and cost.
- **Confirming an action** runs the real API route, so all the normal rules apply. An action can be decided only once (`AI_ACTION_ALREADY_DECIDED`).
- Conversations are listed on the AI page or behind the clock icon in the panel, and can be tied to a recording.

## 17. Data model

### People and phones

- **`person`**: one real human. No phone column. Holds the profile the AI enriches: first/last name, date of birth, gender, address, `preferredLanguage` (default `ar`), and `source` (`call` or `doctor`).
- **`person_phone`**: links a person to a phone (always E.164). `relationship` says how the person relates to the phone's owner: `self` (at most one per phone, enforced by a unique index), `child`, `parent`, `spouse`, `sibling`, `other`. One phone can serve a whole family, and one person can be on several phones.
- **`patient`**: a **doctor ↔ person** link with per-doctor details (CIN, names, address, the number this doctor uses). Medical files, invoices, consultations and recordings point to `patient.id`.

### Practice

- `doctor_profile` (status, cabinet, coordinates, availability JSON, documents, logo/stamp), `doctor_application`, `doctor_unavailability`.
- `secretary`, `secretary_invite`.
- `speciality` (33), `cities` (24).

### Care and money

- `appointment`: doctor, patient, **person** (who it is for), **contactPhone** (who booked), start/end, status, source, `urgent`, `emergencyGroupId`.
- `consultation`, `patient_medical_file` (type, title, description, document links, sent-on-WhatsApp flag).
- `invoice`, `invoice_item`, `invoice_payment` (patient billing).
- `review` (token, rating, wait time, comment).

### Calls

- `call` (Twilio call sid, from/to, status, duration, caller name, recording link, linked appointment), `call_event` (transcripts, function calls with args/results/status, system notes, errors, booked events).
- `call_report`, `blocked_phone`.

### Riaya billing and usage

- `subscription` (one per doctor: plan, status, period, cancel-at-period-end), `billing_invoice` (`kind` = `subscription` or `top_up`, Konnect reference and pay link, amounts in millimes), `whatsapp_usage` (per doctor per month), `recording_usage`, `consultation_recording`, `ai_chat_conversation`, `ai_chat_message`.
- Better Auth tables: `user`, `session`, `account`, `verification`.

### Key modelling decisions

- Phone numbers are **not identity**; the person is. A phone can hold several people.
- `appointment.personId` says who the visit is for; `appointment.contactPhone` says where messages go; the doctor's patient file is linked at accept time.
- Usage is stored as event rows (sends, recording seconds, message costs), not as one overwritable counter, so history is kept.

All use BullMQ with Redis; the workers run in the voice service.

|---|---|---|

### How we tested

A small program acts like a **phone caller** and plays the same **7 sentences** each time: Tunisian Arabic, French and mixed ones such as "نحب ناخذ rendez-vous عند dermatologue". It records what the AI answers and how long it takes, using the real instructions and booking tools. We timed each step on its own. We then built the `/test-call` page to switch engines and run the same call on each. Limit: the test voices were computer voices, not real patients.

### What we learned

- **Tunisian Arabic is the hard part.** For English and French almost every model worked. Few models understand Derja (one returned nothing for Arabic; others dropped or misspelled words; mixed Arabic-French sentences were the hardest). Few voices speak it well; Gemini had the most natural ones. We judged every choice on Tunisian Arabic first.
- **The best models were often the slowest.** Best listening and best voice were also the slowest.
- **Speed adds up in a chain.** The fastest chain we built waited about **6.8 s** before answering; with Gemini for listening and voice it was **over 10 s**.
- **Speed of the chains tested:**

| Step | Model | Finding | Problem |
|---|---|---|---|
| Listening | Microsoft MAI | Best on our sentences, ~0.5 s | Preview product, one provider |
| Listening | Gemini | Excellent text | 2 to 3 s per sentence |
| Listening | Inworld | Fast | Not good in Arabic, worst on mixed sentences |
| Thinking | GPT-5.4 mini | Fast, ~1.2 s to start | Less smart than Claude |
| Thinking | Claude Sonnet | The smartest | 3× slower to start (3.6 s) |
| Voice | Gemini | Most natural | 2 to 3 s before it talks |
| Voice | Inworld | Fast | Only 2 Arabic voices, not perfect |

- **Realtime response times:** Gemini Live answered in 1.6 to 4.5 s (slower when it first called a tool). The Inworld chain was about 2.2 s. GPT realtime had a very good response time and followed instructions well but its pronunciation was not perfect. The first Gemini Live versions (`gemini-3.8-live` and its extended-thinking version) had a good voice and speed but understood poorly, and the extended-thinking version failed to use tool results in 8 of 18 tries. `gemini-3.1-flash-live-preview` was the best of the Gemini family.
- **Testing found real bugs.** The AI saved the caller's name or language on almost every turn, costing ~1 extra second each time. We moved it to a background job (the LiveKit path's `profileCapture`).

### Final choice

We chose **Gemini Live**, with the `gemini-3.1-flash-live-preview` model and the Puck voice. Among the models we tried it had the most natural Tunisian dialect (almost perfect), a very fast response, very good handling of interruptions, and the best understanding and reasoning of the Gemini family. OpenAI Realtime was the smartest in the first tests, but its voice did not have the right accent and it was very expensive. GPT-Live was too artificial and costly, and the chains of separate steps were too slow.

The one weakness is the caller transcript, which Gemini Live produces badly. We solved it with a separate **caller transcriber** (`google/gemini-3.1-flash-lite` through OpenRouter) that feeds the admin live view. All other realtime paths and the LiveKit chain stay in the code on purpose, so they can be compared again.

(The reasons above come from the verdicts in `voice/MODEL_NOTES.md`; the notes do not record a dated decision, so check them against what you remember before quoting them as the team's reasoning.)

## 21. Design decisions and the reasons behind them

### Handling a doctor who refuses or does not answer

We first thought of asking the patient for a **backup doctor** from the start. But we already ask many things and want to ask as little as possible. So we ask for **one doctor**, and if that doctor refuses or stays silent, we **call the patient back** with new options. We will keep testing and may change the approach.

### Prices

Price matters when choosing a doctor, but the real price depends on many things, and patients usually do not know what they need before a diagnosis. We considered letting doctors enter a price per service, but decided **not to show full prices** to patients.

### Geocoding

We compared several geocoding services on Tunisian places: hospitals, universities, train stations and the addresses of doctors' cabinets, written in French. For each query we checked how far the returned position was from the real one. **Google Places was clearly the best**: it knew many more places, including businesses and clinics, and it placed them more accurately. Geoapify and Mapbox were weaker, so Geoapify stayed only a test provider. It is not perfect either, and some addresses exist in several places, so we also give the AI help with **Tunisian cities and places**. A switch (`GEO_PROVIDER`) keeps the other provider available without changing the callers. Road distance for the best-fit polish still comes from the Geoapify Route Matrix.

### Patients have no website

Patients use only the phone and WhatsApp. This keeps the experience simple and matches how people in Tunisia already communicate.

### Doctor's own WhatsApp number

Messages come from the doctor's own number so the conversation stays private and patients recognize the sender.

### AI proposes, the doctor confirms

The assistant never changes data on its own. It prepares a card and the doctor confirms. This keeps the doctor in charge and reuses the same API routes and rules as the normal screens.

### Pay-for-cost AI limits

AI use is limited by real model cost, not by message count, because a long chat with a transcript costs far more than a quick question.

### Free doctors stay in the best-fit search

We considered leaving Free doctors out of the best-fit results, so that they would have one more reason to subscribe. We dropped the idea. Our patients should always get the best service, which means the best-matching doctor, whatever plan that doctor is on.

### Plan limits do not touch patients

Patients are never refused because of a doctor's plan. Phone booking is unlimited on both plans; the doctor's plan has no part in who the AI offers.
